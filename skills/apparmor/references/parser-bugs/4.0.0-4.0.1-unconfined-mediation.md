# `apparmor_parser` 4.0.0 / 4.0.1 — `flags=(unconfined)` + body rules silently demotes to enforce

**Affects:** `apparmor_parser` **4.0.0** and **4.0.1** (stock/unpatched).
**Fixed in:** upstream parser **≥ 4.0.2** (MR!1247, merge commit `4bb134e4`, first tagged `v4.0.2`; 4.0.2 release notes: *"don't add mediation classes to unconfined profiles"*).
**Distro caveat:** the same Launchpad bug (LP#2067900, reported as "unconfined profile blocks pivot_root") was fixed in Ubuntu by a **kernel** revert (Noble kernel 6.8.0-56), and the bug thread says the parser change was reverted in the Ubuntu apparmor package. So a Noble parser reporting `4.0.1` may or may not carry it. Don't gate on a package version string; test the profile's mode (below).

## The bug

On parser 4.0.0/4.0.1, a `flags=(unconfined)` profile that carries **any body rules** — including rules pulled in via `include if exists <local/<name>>` — is incorrectly treated as *mediating* those rule classes. The profile is then **silently demoted from unconfined to enforce**, so operations that were implicit allows under "unconfined" (userns creation, `uid_map` writes, dconf, Wayland connect, etc.) start returning `EACCES`.

The demotion is silent: nothing in `apparmor_parser -QTK` flags it, and the app fails with denials on paths that appear nowhere in your rules — they are collateral from the class-mediation the parser wrongly switched on.

### Canonical trigger

A stub profile that is `flags=(unconfined)` + `userns,` + a `local/` hook (exactly the Electron/Chromium/Firefox userns-stub shape — see `../electron-chromium.md`):

```apparmor
profile firefox /usr/lib/firefox/firefox flags=(unconfined) {
  userns,
  include if exists <local/firefox>
}
```

- Empty `/etc/apparmor.d/local/firefox` → profile stays `(unconfined)` ✓
- Drop **one** deny include into `local/firefox` → profile silently becomes `(enforce)` ✗, and the app dies (content-process sandbox children fail `writing /proc/self/uid_map: EACCES`, dconf write fails, Wayland connect fails).

Adding a kitchen-sink allow (`capability,`/`network,`/`mount,`/`userns,`/`/** rwklmix,`) to the local include does **not** restore unconfined semantics — the bug applies regardless of how permissive the body rules are. `attach_disconnected`/`mediate_deleted` would need to be on the `profile` declaration line (which a `local/` include can't set).

## Rule of thumb (the transferable part)

**A `local/` deny include on a `flags=(unconfined)` stub never buys protection.**

- On an affected parser it demotes the stub to enforce and breaks the app.
- On a fixed parser it leaves the stub unconfined, and an unconfined profile mediates nothing, so the deny rules are inert (`../rules.md` §1 "What `flags=(unconfined)` actually does").

If the goal is to keep the app away from sensitive files, the stub is the wrong place: write a real confining profile (with its own name and attachment) or accept that the app is unconfined.

To check which behaviour a given system has, load the stub with a non-empty `local/` include and read the mode a fresh process gets. `apparmor_parser --version` is not enough, because distro builds keep the base version string:

```bash
sudo apparmor_parser -rK /etc/apparmor.d/firefox
aa-exec -p firefox -- cat /proc/self/attr/current   # from an unconfined shell
# firefox (unconfined) -> no demotion
# firefox (enforce), or cat fails to start -> affected parser: remove the local/ rules
```
